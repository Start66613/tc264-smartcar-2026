# 工程方法论：从"改代码"到"可验证的迭代"

> 这套流程是本项目最大的隐性资产。它跟车无关，跟"怎么在压力下不出错"有关。

---

## 一、核心循环（每个版本都走一遍）

```
   ┌──────────────────────────────────────────────────────────┐
   │  ① 观察：数据里到底是什么现象？                          │
   │      ↓ 记录帧号、数值、时间                                  │
   │  ② 假设：一句话说清"因为 X，所以 Y"                       │
   │      ↓ 必须能被证伪                                        │
   │  ③ 影子验证：不动工程，副本上跑通"复现 + 修复"            │
   │      ↓ 原版复现问题 / 影子显示修复 / 无回归                 │
   │  ④ 报告 → 批准：用户点头才动手                            │
   │      ↓                                                     │
   │  ⑤ 应用：只改一处，备份 .bak_vXXXpre                       │
   │      ↓                                                     │
   │  ⑥ 四门禁：测试 / 编译 / 烧录 / 回读                       │
   │      ↓                                                     │
   │  ⑦ 归档：note + zip + history + INDEX + memory             │
   │      ↓                                                     │
   │  ⑧ 实车：开记录跑，回到 ①                                  │
   └──────────────────────────────────────────────────────────┘
```

**最关键的是 ③**：在 PC 上把"问题复现"跑出来，实车只做最终验证。
本项目 v143/v144/v146/v148 都是这么过的，**没有一次是"烧上去看看"**。

## 二、影子验证的标准做法

### 2.1 目录约定

```
tmp/pre_vXXX/        ← 改之前的快照（基线）
tmp/shadow_vXXX/     ← 打补丁的副本
tmp/elf_vXXX/        ← 该版本的 ELF/HEX 存档（跨版本读数据用）
```

### 2.2 双模式编译

```c
#ifdef EXPECT_SHADOW
    CHECK(s.phase == BR2_TURN);       /* 影子：应该进环 */
#else
    CHECK(s.phase == BR2_ARMED);      /* 原版：应该卡住（复现 bug） */
#endif
```

```bash
gcc -std=c99 -Wall -Wextra -DEXPECT_SHADOW \
    -I scripts/mock_vision -I tmp/shadow_v148 -I firmware/.../code \
    scripts/test_bigring_premouth.c firmware/.../code/cam_image.c \
    tmp/shadow_v148/big_ring.c -o tmp/test_shadow.exe
```

**断言必须双向**：
- 原版必须**失败**（证明 bug 存在）
- 影子必须**通过**（证明修复有效）
- 其他场景必须**都不变**（证明无回归）

### 2.3 一键复验脚本

| 脚本 | 验证内容 |
|---|---|
| `run_blind_shadow_check.py` | v143 盲区降速：原版 1380→2609，影子压到 450 |
| `run_corner_speed_check.py` | v146/v147 弯道提速：硬弯 250→292→334 |
| `run_premouth_check.py` | v148 顺序竞态：4 场景（修复/无回归/过期/单次） |

**价值**：任何一天回来，跑一条命令就能确认"当时的结论还成不成立"。

## 三、四门禁（缺一不可）

| # | 门禁 | 命令 | 通过标准 |
|---|---|---|---|
| 1 | host 测试 | `python scripts/run_vision_host_tests.py` | 12/12 套件全过 |
| 2 | 编译 | `python scripts/build_tc264_servo_check.py ...` | `0 errors, 0 warnings` |
| 3 | HEX 校验 | `python scripts/check_expression_hex.py --project ...` | 仅 PFlash、逐行 checksum 通过 |
| 4 | 烧录 + 回读 | `python scripts/flash_tc264.py ...` + `read_vision_track_report.py` | `FlashVerified=true` + HEX 一致 + `fault=0` |

**为什么"0 warnings"也算门禁**：本项目的真实 bug 里，至少两个最初是以 warning 形式出现的（指针类型不匹配、未使用变量背后的逻辑遗漏）。

## 四、烧录前的两条铁律

### 4.1 先读记录，再烧录

烧录会**清空 RAM**，记录就没了。

```bash
# ① 核对版本
python scripts/read_vision_track_report.py   # 看 hex_sha256
# ② 读记录并落盘
python scripts/read_track_trace.py > tmp/trace_$(date +%H%M).txt
# ③ 抢存帧（如果有）
python scripts/read_camera_frame.py line_trace > tmp/frame.log 2>&1
# ④ 确认无新数据后才烧
```

### 4.2 读板前核对 ELF

**事故**：重编后符号地址漂移 4 字节 → 用新 ELF 读旧固件 → 读出 2421 的假帧数。

**规程**：
1. `flash-result.json` 的 SHA == 板上固件
2. ELF 必须是那个版本的构建产物（`tmp/elf_vXXX/`）
3. 读到的数据先做合理性检查（帧数 ≤2000、相位单调、fault 可信）

## 五、改动边界

| 类型 | 允许改的文件 | 必须核验 |
|---|---|---|
| 环岛逻辑 | **只** `big_ring.c/h` | 环外逐字节零改动 |
| 视觉 | `track_core.c`（分析段） | 控制段不动 |
| 控制 | `track_core.c`（控制段） | 视觉段不动 |
| 记录/诊断 | `cpu0_main.c` | 控制逻辑不动 |

**原则**：**视觉与控制不同批改**。同一个版本里既有视觉又有控制改动，出问题无法归因。

## 六、归档五件套

| 件 | 内容 | 作用 |
|---|---|---|
| `note.md` | 为什么改、改了什么、验证结果、怎么回退 | 三个月后还能看懂 |
| `zip` | 源码 + HEX + 日志 + 测试 | 可重建 |
| `flash-history.md` | 烧录时间、HEX、结果 | 时间线 |
| `INDEX.md` | 版本索引（含 SHA 前 8 位） | 快速查找 |
| `memory` | 长期笔记（当前基线、回退链、遗留问题） | 跨会话延续 |

---

## 七、复盘清单（每次出问题问自己）

1. 这个现象在**哪一帧**？数值是多少？
2. 上次改动是**哪一版**？改了几处？
3. 有没有**同工况的对照**（成功轮 vs 失败轮）？
4. 我的假设**能不能被证伪**？怎么证伪？
5. 如果现在回退，**回得去吗**？HEX 对得上吗？

---

## 八、这套流程的代价与收益

| | 代价 | 收益 |
|---|---|---|
| 影子验证 | 每个改动多 20~40 分钟 | 实车不炸；失败可归因 |
| 四门禁 | 每次多 5 分钟 | 没有"烧坏了不知道" |
| 归档 | 每版多 5 分钟 | 198 个版本全部可追溯 |
| 一次只改一处 | 进度看起来慢 | 避免了 v144 那种"改两处、全回退" |

**结论**：在 7 天的时间里，这套流程**净赚时间**——因为它把"试错"从实车搬到了 PC。
