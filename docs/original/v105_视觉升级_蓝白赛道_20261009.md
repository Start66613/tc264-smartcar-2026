## 一、现场反馈

> "你刚才烧录完，我去跑了，很严重，蓝区也会识别出中线然后乱跑，很严重"

即 v104（HEX `448979E1`）上板后暴露的新症状：**车头前方的蓝色赛道区域也被画出了中线**，
中线一整段落在蓝色地面上 → 舵机跟着假中线乱打。

加上此前的"路口的中线和前面的中线都不对齐"（v104 想治的那个），两次症状**同一个根因**，
v104 只是绕开了症状，没有修掉根因。

## 二、数据驱动的根因（真实帧 A/B，不是推理）

赛道是 **黑胶带（≈40）/ 蓝底（205~220）/ 白色跑道（248~255）** 的三峰灰度分布。
相机 188×120 灰度。用板上 dump 的真实帧 `tmp/frame_gray.bin` 做 A/B
（`scripts/diag_real_frame_ab.c`，同时链接固件真实 `track_core.c`）：

```
二值化：v104(单次全局 Otsu)=169    v105(两级递归 Otsu)=224 (一级=169 level=2)

A) v104 单次全局 Otsu thr=169  valid=1 rows=83 measured= 3 model=80 degraded=1
   中线跑出白路(落黑/蓝)的行=30   落在"幽灵白"上的行=26   中线x范围=61..62

B) v105 两级递归 Otsu thr=224  valid=1 rows=83 measured=68 model=15 degraded=0
   中线跑出白路(落黑/蓝)的行= 4   落在"幽灵白"上的行= 0   中线x范围=26..70

结论：中线跑出白路（落在蓝底/黑区）的行数  A(旧)=30  ->  B(新)=4
```

| 指标（同一真实帧） | v104 单次全局大津 | v105 两级递归大津 |
|---|---|---|
| 二值化阈值 | 169（**落在蓝底 205 之下**） | 224（蓝底之上、白路之下） |
| 中线跑出白路的行 | **30 / 83** | **4 / 83** |
| 其中落在"幽灵白"（蓝底被当白）上 | **26** | **0** |
| 可信测量行 `measured` | 3 | **68** |
| 模型补出行 `model_rows` | 80 | 15 |
| `degraded`（过路口限速） | 1 | 0 |
| 中线 x 范围 | **61..62（冻死不动）** | 26..70（跟着路走） |

**两条独立缺陷：**

### 缺陷 1：全局大津法把"蓝底"和"白路"一起判成白（蓝区误检的直接原因）

三峰直方图下，单次二分只有两种切法：

- 切在**黑胶带 | (蓝+白)** —— 类间方差通常**更大**，于是算法选它 →
  **蓝底和白路一起是"白"**。阈值 169 落在蓝底（205~220）之下，蓝底在二值图里全是 255。
  任何一行看过去，"白段"都横跨整幅宽度（真实帧 y=90 行白段 `(11,186,176)`，
  其中大半是蓝底）。逐行取中点，中线自然落到蓝区上。
- 切在 **(黑+蓝) | 白** —— 这才是我们要的，但它的类间方差更小，单次大津法**不会选它**。

> 这正是 v103"路口中线不对齐"的**同一个根因**：当时把 `r=186` 顶到画面边缘的行
> 归类成"贴边段"不参与测量，是**绕开**症状；v104 的"可信测量 + 模型插值"进一步
> 把这种行的中点剔掉——但**剔掉之后那 80 行全部靠插值**，`measured` 只剩 3 行，
> 中线于是被冻结在 61..62，`degraded=1`。地表看起来"对齐了"，实际是**把整幅中线的
> 主动权交给了上一帧**，蓝区一样在被当白。

### 缺陷 2：单点连续性闸门 —— 中线会横跨中间的暗缝

旧算法逐行挑"离上一中心最近的那一条白段"，只用**一个中点**做连续性闸门
（`|Δcenter|>35` 就丢该行）。路口 / 岔口 / 环内蓝洞的行，上下两条可信行可能落在
**不同分支**上，插值出来的中线就会横跨中间那条蓝缝
（历史 v006/v021 反复出现的"横跨蓝区抄近道"）。

## 三、v105 改动

### A) 二值化：两级递归大津法（`code/cam_image.c:cam_otsu_two_level()`）

一级分"暗|亮"；若**亮类占比 > 62%**（说明一级只把黑胶带分出去了，蓝+白被打包成亮），
就对**亮类**再重建直方图、再跑一次 Otsu，得到"**蓝底 | 白路**"的分界。

```c
#define OTS_L1_GUARD_PCT 62u   /* 一级亮类占比超过它(%) → 只分出了黑胶带 */
#define OTS_L1_MIN_SEP   10u   /* 二级阈值必须比一级高这么多才有意义 */
#define OTS_L2_MIN_RANGE 12u   /* 亮类内部灰度跨度小于它 → 不是真的双峰 */
```

两条兜底，保证**不会比一级更差**：

- 亮类内部灰度跨度 `< 12`（不是双峰，例如普通灰底赛道）→ 直接返回一级阈值；
- 二级阈值没比一级高 > 10 → 不采用，返回一级阈值。

新增诊断量：`cam_thr1`（一级阈值）、`cam_otsu_level`（1/2）、`cam_bin_suspect`
（二值后白占比 > 72%，很可能整帧不是赛道）。

> **不照搬国赛系数**：国赛队伍普遍用"大津法 + 偏置/形态学"（NEUQ `TS_OTSU_with_bias`、
> CQU `Fast_otsuThreshold`+`image_filter`、engmarkc `camera.c` 白线检测）。
> 本实现是按**本车三峰场景**（黑 40 / 蓝 205~220 / 白 248~255）推导出来的**递归结构**，
> 阈值、跨度、占比全部由本车实测量级决定，没有任何一个数字抄自参考工程。

### B) 中线：左右边线各自分离 + 双边界连续性（`code/track_core.c:vt_analyze()`）

对齐国赛二维视觉的通用做法——**逐行求左右边线、中线 =(左+右)/2**
（CQU `findline.c` 的八邻域搜线 `get_left`/`get_right`、caipingjiang `my_image.c` 的
`boder_L`/`boder_R`/`boder_M`、HammerTa `IMG_DEAL.c` 双边线）。三遍结构：

| 遍 | 做什么 | 关键判据 |
|---|---|---|
| 1 | 逐行提取白段（每行最多记 `VT_SEG_K=4` 段），按形状分类 | 段宽 `[VT_SEG_MIN=12, VT_SEG_MAX=150]`；≥`VT_FULL_W` 判"整行铺满" |
| 2 | 从画面**最下方 14 行**取"种子行"，**向上**逐行跟踪 | **左端与右端同时**落在上一行窗口内（`VT_EDGE_WIN=12`），且宽度落在学习宽度的 `40%~250%` |
| 3 | 可信测量行直接取值；其余行用最近可信行插值/外推 | 与 v104 同思路，但因为第 2 遍已保证可信行**同分支**，插值是安全的 |

```c
/* 第 2 遍：向上逐行，双边界都要连续 */
if(dl>VT_EDGE_WIN||dr>VT_EDGE_WIN)continue;                        /* 左右都要连续 */
if(exp>=16&&(w*100<exp*VT_WID_LO||w*100>exp*VT_WID_HI))continue;   /* 宽度要合理 */
```

**为什么这样就治好了蓝区误检**：
1. 二值化后蓝底 = 黑，蓝区里**根本不存在白段**，也就没有"蓝区上的中线"可言；
2. 双边界连续性在**结构上**禁止中线跨过中间的暗缝跳到另一段白上——
   要跨过去，左端和右端必须同时跳 `>12px`，这是不可能的。

种子行的取法保留了 v104 的时间连续性（在"与该行最宽段同量级 ≥3/4"的段里挑离
上一帧中心最近的），既排除小的反光/噪声斑，又用上上一帧信息。

### C) 单边贴边补线（对齐国赛"单边丢线用另一边 + 学习路宽补线"）

急弯时白路会跑出画面**左右边缘**，被裁掉那一侧的边界根本看不见。
旧做法的后果：整行丢掉 → 该行没有测量值 → 只能冻住上一帧（v104 冻结中线的老毛病）。
国赛的通用解法是：**只要可见的那一侧仍然连续，就用学习到的路宽把另一边补出来**
（HammerTa `IMG_DEAL.c` 的 `TrackWild[row]/2`、CQU `findline.c` 的补线思路）。

具体落地：

1. 逐行单独记录**贴边白段**（这一侧顶到画面边缘的段）：左贴边存它可见的**右端**，
   右贴边存可见的**左端**。这类段因为被裁，宽度会超过 `VT_SEG_MAX`，进不了正常白段池。
2. 建一张**逐行预期路宽表** `vt_wfit[]`：优先用本行学到的宽度；本行还没学到
   （典型情形是它一直贴边、从来没在画面里完整出现过）就借用最近一行学到的
   ——路宽随 y 是平滑变化的，相邻行借过来足够准。
3. 取中点时用"可见边 ∓ 路宽/2"而不是 `(l+r)/2`：

   | 情形 | 可见边 | 旧（当被裁边是真边界） | v105 |
   |---|---|---|---|
   | 右贴边，可见左端 `l` | `l`（127~187） | `(l+187)/2` | `l + 路宽/2` |
   | 左贴边，可见右端 `r` | `r`（0~60） | `r/2` | `r − 路宽/2` |

4. **种子行也做同样修正**——急弯时最下面那几行恰恰是最典型的贴边行，
   种子行的中心偏了，整条中线的"起点"就偏了。
5. 兜底：最下方十几行整段都在画面外（`vt_sn==0`，正常种子找不到）时，
   允许用"贴边段可见边 + 路宽"当种子（仍要求推出来的中心离上一帧不太远），
   否则整帧建立不起任何测量、中线又被冻住。

**实测收益**（`scripts/test_vision_clipline.c`）：

| 场景 | 旧做法中点 | v105 中点 | 真实中心 |
|---|---|---|---|
| 右急弯，可见段 `150..187` | 168 | **181** | 181 |
| 左急弯，可见段 `0..50` | 25 | **19** | 19 |

合成急弯场景（1.6 px/行的边界斜率）的**跟随误差：最大 6 px → 最大 0 px**。

**不污染统计**：贴边行算进 `measured` 与 `clip_rows`，但
**不参与**宽度学习、也不参与环岛判据用的 `open_left/right`、角点、直道统计
——那些必须只用真实双边界，免得把推断出来的边当成事实。

第 3 遍保留 v104 的 `measured` / `model_rows` / `degraded` 语义，
`modeled >= VT_MODEL_DEGRADE(24)` 仍触发过路口限速。

1. **蓝区不再出现中线**：把车放到蓝底区域/路口，屏幕上黄点中线应只落在白路上；
