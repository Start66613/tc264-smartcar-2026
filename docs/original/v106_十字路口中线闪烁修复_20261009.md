## 一、现场反馈

> "十字路口还是看不到中线，但是之前是十字路口没有黄线，现在是十字路口的黄线一直在屏幕左边和中线两个地方闪烁"

拆成两条：
1. **路口仍然看不到（竖直的）中线** —— 这个老问题没解决；
2. **新增症状**：中线在两个位置之间**逐帧跳**：一个是屏幕左边（x≈7），一个是中线（x≈94）。

"闪烁"两个字是决定性线索：中线在两个固定位置之间来回跳，说明**不是插值抖动，而是整帧的"起点"在两帧之间换了地方**。

---

## 二、根因（真实帧证据，不是推理）

用板上 dump 的真实路口帧 `tmp/frame_gray_v102_crossing.bin`（188×120，两级 Otsu 后**白像素 77%**）回放固件同一份代码。

### 改动前的逐行真相（`scripts/diag_cross_frames.c`）

```
路口帧: 一级Otsu=199  两级Otsu=235 level=2  白=17285(77%)
  y  class   n  segs(l..r)                 mid
110  FULL    0  -                           7
109  FULL    0  -                           7
...（中间 79 行全是 FULL）
106  OK      1  0..15                       7     ← 唯一幸存的"白段"
105  FULL    0  -                           7
...（其余也全是 FULL）
种子行 y=106 段[0]=0..15 中点=7 学习宽=0 上一帧中心=94
结果: valid=1 measured=1 model=82 degraded=1 mid=7
```

**83 行里 82 行是 `FULL`（白段 ≥186，整行铺满横向道路）→ 全部被排除；唯一幸存的是 y=106 上一个 `0..15`、16px 宽的贴左边缘小白斑。**

它被当成种子：
- 种子中心 =(0+15)/2 = **7**（屏幕最左）；
- `学习路宽=0`（`vt_wfit[106]=0`）→ 连"单边补线"都补不出来（那条路要求路宽已知）；
- 于是 `measured=1`，**其余 82 行全部从 x=7 插值** → 整条中线画在屏幕最左。

而只要某一帧那个小白斑换到别的位置、或者干脆消失，种子就会落到真正的近处路面上 → 中心 x≈94。**两帧之间就是"屏幕左边 ↔ 中线"的闪烁。** 同一根因也解释了第 1 条症状：路口那一帧的中线根本不是"看到的路面"，所以既不竖直也不可信。

### 两条独立缺陷

**缺陷 1（决定性）：种子的资格判据完全不看"这白段像不像一条路"。**

种子循环只做了一件事——"在该行所有白段里，挑离上一帧中心最近的"，外加一个"宽度 ≥ 该行最宽段的 3/4"。当一行只有一条白段时，后者恒真，等于没有门槛。于是一个 16px 的反光/边缘白斑（而学到的路宽是 ~90px）就获得了决定整条中线的权力。

对照：`vt_take_row()`（逐行跟踪）**本来就有**宽度合理性闸门（`VT_WID_LO=40%` / `VT_WID_HI=250%`），所以逐行跟踪不会犯这个错。**这个闸门漏在了种子上。**

**缺陷 2：路口缺少"横向白带铺满画面"这个全局判据。**

十字路口的本质特征是：横向道路的白在画面上形成一整条**铺满左右**的白带，于是大量行是 `FULL`。这是一个与赛道形状无关、只在路口/环岛入口出现的判据，但 v105 只把它用于"这一行跳过"，没有上升为"整帧正在穿路口"。

代价就是：路口时整帧只剩下零零星星几行"残缺白斑"，而算法**没有任何机制**说"这几行不可信，我该顶住上一帧中心"。

## 三、v106 改动（两处，都在 `code/track_core.c`）

### A) 种子资格闸门（`vt_seed_ok()`）—— 治"闪烁"的直接手段

```c
/* 一个白段能不能当"整帧种子"。种子的中心会决定整条中线（其余行都从它插值），
 * 所以它必须是**可信的路面横截面**： */
static int vt_seed_ok(int y,int l,int r)
{
 int own=vt_wfit[y],w=r-l+1;
 if(own>=16)return w*100>=own*VT_WID_LO&&w*100<=own*VT_WID_HI;  /* ① 路宽已知 */
 return l>2&&r<VT_W-3;                                         /* ② 路宽未知 */
}
```

| 情形 | 判据 | 为什么 |
|---|---|---|
| 学习路宽已知（≥16） | 宽度必须落在 `40%~250%` 学习路宽内 | 与 `vt_take_row` **同一条闸门**。路口那个 16px 白斑 vs 学到 90px 路宽 = **18% < 40%** → 淘汰 |
| 学习路宽未知（刚复位/整帧过曝） | 只接受**两端都可见**的白段 | 贴边白段一侧被画面裁掉、又没有路宽可补，中点纯属瞎猜 |

这条闸门对**急弯贴边补线零影响**：急弯的贴边白段（可见 38px / 学习路宽 62px = 61%）稳稳过闸门（实测 `test_vision_clipline` ② 仍是 181、③ 仍是 19）。

### B) 十字路口判据 + 顶住（`crossing` / `hold`）

```c
/* 一帧里 FULL 行 >= 24（分析带共 83 行，≈29%）且可信测量行 < 8
 * → 判定"正在穿十字路口"，用上一帧中心直着顶过去。 */
int crossing=(full_rows>=(int)VT_FULL_MIN_ROWS)&&(ok_rows<(int)VT_OK_MIN),hold=0;
if(ok_rows==0||crossing){
 if(max_w>=VT_W/2&&t->previous_mid>0){
  /* 全帧按上一帧中心铺成一条竖直线；all_white=1 + degraded=1 交给 controller */
  ...
  v->all_white=1;v->degraded=1;hold=1;
 }
}
...
v->valid=valid>=20u&&near>=6u&&wsum>0&&ok_rows>0&&!hold;
```

- **为什么判据用 FULL 行数，而不是"白段太宽"**：急弯每行只有一条窄白带、其余是暗的，**永远凑不出 FULL 行**；只有横向道路才会让白铺满左右。所以这条判据天然不会误伤急弯。
- **`previous_mid` 不会被污染**：`hold` 帧 `v->valid=0`，而 `t->previous_mid` 只在 `v->valid` 分支里更新 → 路口期间它一直锁在"进路口前最后一次真实路面中心"，路口走完立刻能接回来。
- **行为等价于既有的"降级"通道**：`valid=0 + degraded=1` 正是 v101/v102 已经验证过的"近处有线、远端没了"的降级控制（`test_vision_track_lost_recover` 第 3.5 节），限速到 `VT_DEGRADE_SPEED=320`、不停车。
- **2s 兜底仍然生效**：`all_white` 连续 100 帧（≈2s）→ `VT_LOST` 停车。正常穿一个路口只要几百 ms，够用；真在白墙前杵着 2s 才停。

新增常量（`code/track_core.h`）：

```c
#define VT_FULL_MIN_ROWS 24u   /* FULL 行数门槛（分析带 83 行，≈29%） */
#define VT_OK_MIN        8u    /* 可信测量行下限；低于它 + FULL 行多 → 判路口 */
```

## 五、待实车验证清单（通电后）

1. **路口中线变竖直**：进十字路口时，屏幕上的黄点中线应**保持一条竖直直线**（顶在进路口前的中心），不再左右闪；
2. **不再跳到屏幕左边**：路口全程 `mid` 应该落在画面中部的合理区间，不应出现 x≈7 这种贴左的值；
3. **不误停车**：穿路口期间应保持行驶（v106 走 degraded 限速 320），不应触发 `VT_LOST`；
4. **路口之后立刻接回**：出了路口、下方重新出现真实路面横截面时，中线应马上恢复跟线，`valid` 回到 1；
5. **回归不破**：蓝白赛道直道/弯道手感不变；急弯贴边时中线仍跟着白路走到画面一侧（`clip_rows>0`）；
6. **反例**：真的冲出赛道 / 对白墙 → 连续 2s 全白后仍判 `VT_LOST` 停车。
