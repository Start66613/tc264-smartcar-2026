# 经验与教训：30 条踩坑实录

> 每条都标注了"证据"——对应版本、帧号或数据文件。
> 排序原则：**能救命的排前面**，不是按时间顺序。

---

## A. 方法论（6 条，最值钱）

### A1. 先数据后改动，否则就是赌博

**教训**：凭感觉调参时，你无法区分"变好了"和"换了个地方犯错"。

**做法**：
- 每次实车都开记录（P20.7 短按）。
- 改动前先问：**哪一帧、哪个数值、哪个现象**说明这里有问题？
- 改完用同一段路况复测，对比同一指标。

**证据**：v143 盲区降速不是拍脑袋——是 6 次失败记录（run3/7/8/11）共同指向"环内 ≥1s 长盲区"，才定位到"PI 在盲区里反向加油"。

---

### A2. 影子验证：不动工程，先把方案跑一遍

**做法**（本项目定型流程）：

```
1) 复制 track_core.c/.h（或 big_ring.c/.h）→ tmp/shadow_vXXX/
2) 只改副本
3) 写一个"双模式"测试：同一组输入喂两版，断言各自预期
   - 原版：必须复现问题
   - 影子：必须显示修复
4) gcc 编两份可执行文件，跑同一工况对比
5) 产出"待批准"报告，附数值对照
```

**收益**：v143/v144/v146/v148 全部在 PC 上先把"问题复现 + 修复生效"跑通，实车只是验证，不是摸索。

**证据**：`scripts/run_blind_shadow_check.py`、`run_corner_speed_check.py`、`run_premouth_check.py`——三个一键复验脚本，随时可重跑。

---

### A3. 四门禁：少一道都不算完

| 门禁 | 判据 | 为什么必须有 |
|---|---|---|
| ① host 测试 | 全部套件通过（本项目 12 套件） | 防止"改 A 坏 B" |
| ② 编译 | 0 errors, **0 warnings** | 警告里藏着真 bug |
| ③ 烧录 | `FlashVerified = true` | 写入完整性 |
| ④ 回读 | HEX 一致 + `fault=0` + 相机在推进 | 证明"跑的是这版" |

**教训**：有一次只看"烧录成功"就以为完事，结果回读发现 `cam_adv=False`——相机根本没出图，白跑一轮。

---

### A4. 一次只动一处

**反例**：v144（环内盲区注入）同时改了两件事，实车失败后无法判断是哪一处的问题，只能整体回退。

**正例**：v146 只改两行限速公式（同一类参数），影子验证给出精确数值（硬弯 250→292），实车行为可预期。

**推论**：如果一次必须改两处，那这两处必须**属于同一个物理量**（例如同一条限速公式的两个系数），否则拆开。

---

### A5. 版本必须能"字节级复现"

**做法**：每次改动前 `cp x.c x.c.bak_vXXXpre`；回退时 `cp` 回来重编，**比对 HEX SHA256**。

**为什么重要**：这是唯一能证明"烧的就是当时验证过的那份"的方法。本项目多次验证成功：

```
回退 v148 → 重编 → 47743D54（与原始构建一致）
回退 v147 → 重编 → 8DDA1A37（一致）
回退 v146 → 重编 → C4E5B2DC（一致）
回退 v143 → 重编 → BE6E1A07（与 run12 成功轮一致）
```

**反面案例**：曾用"新 ELF + 板上旧固件"去读内存，因为符号地址漂移，读出一堆垃圾（line_trace_count 读出 2421 的假帧数，相位序列全是假的）。

---

### A6. 归档不是形式主义

**每版五件套**：`note（为什么改）` + `zip（源码+HEX+日志）` + `history（烧录史）` + `INDEX（版本索引）` + `memory（长期记忆）`。

**收益**：一个月后回来写总结，能准确说出 v146 改的是哪两行、v147 为什么被回退。**没有归档，这些就只剩"好像改过"**。

## B. 视觉（8 条）

### B1. 蓝白赛道：一级 Otsu 一定会把蓝白合并

| 项 | 内容 |
|---|---|
| 症状 | 车在蓝区"看到中线"，一头扎进去 |
| 误判 | 反复调灰度阈值（无效） |
| 根因 | 一级 Otsu 只分出"黑胶带 / 非黑"，蓝底和白路同属亮类 |
| 解法 | 亮类占比 >62% → 对亮类**再跑一次 Otsu**，得到"蓝 \| 白"分界 |
| 版本 | v105 |
| 证据 | 同一帧 `measured` 7 → 46 |

---

### B2. 贴边行的中点，必然是错的

**原因**：白段被画面边缘裁掉一半，剩下的中点偏向被裁侧。

**做法**：只用"左右边界**都在画面内**"的行作为**测量值**；其余行用同帧最近可信行**插值/外推**。

**收益**：近处和远处的中线来自同一条模型，**天然对齐**，不再出现"底下 x=101、上面 x=160"的断崖。

**版本**：v104。

---

### B3. 种子资格闸门：一个 16px 边斑能劫持整帧

**症状**：路口黄线在 x≈7 和 x≈94 之间逐帧跳。

**根因**：83 行里 82 行是"整行铺满"，只剩 y=106 一个 16px 贴边小白斑；它被当成种子 → 中心 x=7 → 整条中线画到最左。

**关键洞察**：逐行跟踪**本来就有**宽度闸门，唯独**种子**没有。一行只有一条白段时，"宽度 ≥ 该行最宽段 3/4"恒真，等于没门槛。

**解法**：种子必须过 `vt_seed_ok`（宽度/位置/形态三合一），与追踪共用同一闸门。

**版本**：v106。

---

### B4. 判据要在循环外求值（防死锁）

`vt_analyze()` 是**近→远**扫描：近处行的 `valid` 还没算出来时，就用它当补线前提 → 补线永不触发。

**解法**：循环内只收集证据，**循环结束后**再统一判定。

**版本**：v103。

---

### B5. 路口重建必须覆盖 `edge_mode == 3`

**教训**：静态回放默认 `edge_mode=0`，实车过路口是 3。曾出现"静态修好了、实车照旧折左"。

**做法**：所有路口/远端重建分支，测试必须带 `--edge3`；两套模式都要过。

**版本**：v107 → v116。

---

### B6. 盲区不是阈值问题（最重要的一条）

**9 张自动存帧，直方图高度一致**：

```
过曝 ≥240    55% ~ 80%
中间调       26% ~ 37%
暗部 <100    < 1.5%
```

**结论**：画面里**真的没有线**。低对比度 + 大面积过曝 + 几乎没有黑像素 = 信息物理缺失。

**所以**：
- ❌ 调阈值 —— 无效
- ❌ 换局部自适应阈值 —— 无效（这是后来才确认的）
- ✅ **行为兜底**（降速 + 保持转向）—— 唯一正解

**证据**：`outputs/run5_blind_frame_auto.png` 等 9 张图；`docs/05_数据资产.md` 有清单。

---

### B7. 环岛失败与"环内长盲区"强相关

| 轮次 | 结果 | 环内长盲区 |
|---|---|---|
| run1/run2/run5 | 成功 | 无（≤4 单帧） |
| run3 | 失败（飞出） | 1.8s 全白 |
| run7 | 失败（停车） | 进 LOOP 首帧即全盲，盲飞 2.4s |
| run8 | 失败 | 有 |
| run11 | 失败（爬行后停） | 有 |

**推论**：环岛的"控制问题"里，有一半其实是"看不见"的问题。先解决看得见/看不见时的行为，再谈转向参数。

---

### B8. 摄像头接缝/镜像是硬件级问题，别在算法里找

- 图像撕裂 → DMA 完成中断内快照（v079）
- 左右反 → `CTRL_MID_MIRROR` 翻转（v079）
- 1px 浅缝被 Otsu 判成黑 → 白段被切成两段 → 追踪链断 → 中线整条竖直外推（v136）

**教训**：当"中线突然变成一条直线"时，先怀疑**二值化把路切断了**，而不是控制算法。

## C. 控制与状态机（7 条）

### C1. 盲区里 PI 会"反向加油"

**机制**：丢线降速路径**排除了 `all_white` 帧** → 盲区时 PI 照常运行 → 反馈低 → 误差持续为正 → 积分每拍 +34 → PWM 从 648 爬到 1980/2820。

**现象**：越看不见越加速。

**解法**：连续 ≥2 拍无有效线 → 强制压爬行档、**跳过 PI**。

**版本**：v143。**这是全程最关键的一个修复。**

---

### C2. 全白帧的"转向冻结"是给路口设计的，在环岛里是灾难

**机制**：`reliable_steering` 在不可信时冻结上一次舵角。路口直行时正确；环岛里如果冻结在"回正帧"（-4.8°），车就转不过弯。

**教训**：**同一个保护策略在不同场景下语义相反**。环岛需要的是"保持环向转向"，不是"保持上一帧"。

**版本**：v144 尝试注入合成线（失败/回退）；v143 的速度维度先解决了主要矛盾。

---

### C3. 反打保护必须有数据阈值

**症状**：出环右偏，想左修正，却被强制右打（更右偏）。

**证据**：run13 f117-121 记录 `mid=80` 连续 5 帧 = 注入 118；而车的原始需求是 raw 70-79。

**解法**：阈值 80 → 60（raw 60-79 放行；<60 仍反打，防"往回跑"）。

**验证**：复古数据 `ring_backwards_0428` 里"往回跑"核心段 raw 28-60，仍在保护范围内。

---

### C4. 状态机要防"确认顺序竞态"

**症状**：run15 全程正常，就是**不进环**。

**根因**：
```
f135-136  口特征命中 2 次（确认级）→ 但还在 OFF 未武装 → 证据被丢弃
f138      武装特征确认 → 进入 P1
f140+     口特征再未出现（车已开过）→ 永远等不到 → 卡死
```

**关键洞察**：特征是**事件流**，不是剧本。哪边先凑齐 2 次命中靠运气。

**解法**：OFF 期跟踪"口"的预确认；武装确认时若 1.2 秒内口刚确认过 → **直接进环**。窗口外不补救（防误触）。

**版本**：v148（影子验证 4 场景全绿）。

---

### C5. 检测器标定必须覆盖"位置/亮度变体"

**教训**：只按一张标定图调参数，实车走线偏 5px 就完全失效（v133 首跑全程未触发）。

**做法**：以三帧为种子，合成 **30 个平移/亮度变体** + 8 个负样本，做参数搜索，得到 ±20~30px / ±8行 的容忍度。

**版本**：v134。

---

### C6. 保险丝要有，但不能掩盖问题

- 8 秒强制关闭环岛模块（v141）：防止状态机卡死后永久注入。
- 2 秒全白停车：防止彻底迷路。
- 500ms 失联停车（遥控固件）。

**教训**：保险是**最后一道**，不是第一道。run13 的 7.6 秒僵持，就是两个保险互相抵消的结果。

---

### C7. 差速转向要"内轮减速"，不是"外轮加速"

**做法**：`内轮 = pwm × (100 - duty/2) / 100`，外轮全速。

**原因**：外轮加速会让车在弯里"推头"，内轮减速才产生有效的横摆力矩。

**证据**：学长国赛代码 + 本项目实车对比。

## D. 工程与硬件（9 条）

### D1. 舵机中位是 740，不是 750

- `740 raw = 1480us` 才是本车真直。
- 750 会持续左偏，肉眼在直道上能看出来。
- **所有**固件（含遥控）统一 740。

---

### D2. IMU 初始化顺序：屏幕先，IMU 后

**症状**：IMU 先初始化 → 屏幕花屏 / IMU 失联。

**解法**：`ips200_init()` → `imu660ra_init()`。与已验证的 IMUCheck 工程一致。

**版本**：v028。

---

### D3. P10.5 / P10.6 是 boot 引脚

逐飞明确警告：P14.2-14.6、**P10.5、P10.6** 属 boot 引脚，不合理使用会导致无法启动。

但遥控接收机的官方示例就是 **SBUS → P10.6（UART2）**。结论：**能用，但接线/上下电顺序要小心**，且不要在这两个脚上做推挽输出。

---

### D4. CPU0 DSRAM 是连续分配，余量只有 ~18KB

- 加 28 字节变量也曾触发 `ltc E112 (cannot locate N sections)`。
- **加任何 CPU0 变量前，先用 ELF + objdump 算余量。**
- 腾挪手法：诊断数组缩容（`ring_diag` 128→64/32→16，回收 5.7KB）。

---

### D5. 读板子内存，ELF 必须和板上固件匹配

**事故**：重编后符号地址漂移 4 字节，用新 ELF 读旧固件 → 读出 2421 的假帧数、假相位序列。

**规程**：
1. 先确认板上 HEX SHA（`flash-result.json`）
2. 确认 ELF 是那个版本的构建产物
3. 每版存档 ELF（`tmp/elf_vXXX/`）
4. 读到的数据先做合理性检查（帧数 ≤2000、相位单调合法、fault 码可信）

---

### D6. 读存帧，绝对不能接 `| head`

**原因**：`head` 提前关管道 → Python 收到 SIGPIPE 中断 → `frame_saved.bin/png` **残留上一次的旧文件** → 看起来"两帧一模一样"。

**正确做法**：
```bash
python scripts/read_camera_frame.py line_trace > tmp/read.log 2>&1
# 然后对 bin/png 做 sha256 核验，连续两次读必须不同
```

---

### D7. 一个工程里可能混着 CRLF 和 LF

**实测**：`big_ring.c` = 纯 LF；`big_ring.h` = CRLF；`track_core.c` = LF；`test_bigring_rev_fsm.c` = CRLF。

**教训**：改文件前先诊断行尾（`b.count(b'\r\n')` vs `b.count(b'\n')`），写回按原样。

**踩坑链**：假设 CRLF → assert 失败 → 改成按行处理 → 又被 LF/CRLF 混合坑 → 最后用"shadow 内容 normalize 后整体写入"才稳。

---

### D8. `hot attach error 0x4` = 调试链接不在，不是固件坏了

**两次实证**：车被拿走 / 下载器断开时，必然出现；重试 30 次也没用。

**判别**：烧录已完成（`FlashVerified=true`）的情况下，这个错误**不影响固件**，只影响回读。

**正确处置**：接回下载器 + 供电，等 10 秒再读。

---

### D9. 烧录会清 RAM，记录必须先读

**铁律**：烧录前必做两件事——
1. 读板上记录并落盘（`read_track_trace.py`）
2. 读板前核对 ELF 与板上固件版本

**教训**：曾因先烧后读，丢掉一整轮 862 帧的成功记录。
