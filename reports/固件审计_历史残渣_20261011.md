## 3. 残渣引起的连带隐患（本轮增量发现）

1. **`grep` 污染**：同一符号在残渣副本与正式源码中同现（轮2 已证实 `LineStartupLimit`、`img_threshoid` 案例）。残渣集中在 `code/` + `user/` **同目录**，任何"全目录搜索改参数"的操作都可能命中旧副本。
2. **回滚误用**：`firmware/TC264_VisionTrack.zip`（10-09 陈旧）与 `_versions/` 内 10 个快照并存，无版本校验 → "找最新备份"时易选错。
3. **命名三套并存**（`.rejected_` / `_rejected` / `.c.vNNN_rejected` / `bak_brv1` / `_marked`）→ 无脚本能可靠"一键清残渣"，未来只能人工枚举。
4. **`_versions/` 无 GC 策略**：`INDEX.md` 只追加不回收，141 个快照已 403 MB，随现役工程继续快照将持续膨胀。

## 4. 一次性清理方案（不改，只给）

**原则**：先归档、后删除；每一步可独立回滚；P0 删完必须重编译比对 hex。

```
步骤 0  备份（必须）：把整个 firmware/TC264_VisionTrack 打包到
        firmware/_versions/TC264_VisionTrack_before_cleanup_<日期>.zip
        （复用现有 build_flash_snapshot.py 的打包逻辑，保持命名一致）

步骤 1  P0 归档：把 74 个残渣移入 code/_trash_v142/ 与 user/_trash_v142/
        （用移动而非删除，观察 1~2 个开发日后再物理删）

步骤 2  P0 删 #if 0：track_core.c 473–511、cpu0_main.c 2893–2983
        （纯文本块，删除后立即重编译；预期 hex 零差异）

步骤 3  重编译 + 校验：
        - 用现有构建流程产出 Debug/TC264_VisionTrack.hex
        - 与清理前 hex 做 SHA256 比对 → 必须一致；不一致立即回滚

步骤 4  P1 归档：firmware/ 根 20 个 zip → firmware/_zip_archive/
        _versions/ 中 Senior6_* 仅留最新版，其余 → _versions/_archive/
        scripts/edit_v*|apply_v* → scripts/_archive/

步骤 5  P2 请示：前身工程目录 / 安装包 / docs·tmp·reviews 的保留阈值由用户定
```

**风险护栏**：
- 第 1 步若发现 `code/_trash_*` 目录名与 TASKING 工程的 `code/` 源路径 glob 冲突（当前源枚举在 `.cproject` 显式列文件、非通配），需改名 `_trash_` → `zz_trash_` 以确保排序靠后；**清理前须确认构建枚举方式不因新增子目录报错**。
- 轮2 已确认：`scripts/diag_*.c` 直接 `#include "track_core.c"/"big_ring.c"` → **清理不得触碰 `track_core.* / big_ring.* / cam_image.*` 的正式文件**，只动 `.bak_*` 后缀副本。
