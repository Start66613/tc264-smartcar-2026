### ⚠️ B-1（**中 · 必现**）丢线计数器被压成布尔 → 挣扎分支死代码

**位置**
- 写入端：`code/track_adapter.c:123`
  `line_out_lost_count = controller.fault==VT_LOST ? 31u : 0u;`
- 读取端：`user/cpu0_main.c:3323` `if (line_out_lost_count > LOST_GIVEUP)`，`:3377` `else if (line_out_lost_count > LOST_STOP_LIMIT)`
- 阈值：`code/PID.h:14` `LOST_STOP_LIMIT 8u`，`code/PID.h:16` `LOST_GIVEUP 30u`

**场景**：`PID.h` 的设计意图是"连续丢线 8 帧→进入挣扎 / 30 帧→彻底放弃"。但**新控制链（vt_step）把该变量当成布尔量写**：`controller.fault==VT_LOST` 为真时直接写 **31**，否则写 **0**。全工程搜索确认**没有任何 `line_out_lost_count++`**（仅 4 处写：`track_adapter.c:56/123`、`cpu0_main.c:3179/3350`，后两处是清零）。

**后果**（均为必现，已逐条核对该变量的全部消费者）
1. `else if (line_out_lost_count > 8)` 要求取值落在 **9..30**，而变量只能取 **0 或 31** → **该分支永不执行**（死分支）→ `cpu0_main.c:3377-3386` 的 `draw_state_row(ST_STOP)`（"丢线停车（挣扎中）"提示）**永远不显示**。
2. **两段式语义塌缩为一段**：`PID.h:13-16` 的设计意图是"连续丢线 8 帧 → 提示 / 30 帧 → 彻底放弃"，中间的 **9..30 区间（"还在挣扎"的中间态）在数据上根本不存在**。`> 30` 在首次置位（=31）时立即成立 → 两级阈值退化为单级。
3. **诊断量退化**：该变量同时被 `cpu0_main.c:1226`（屏幕）、`:1913`（`line_senior_report.lost_count` → DAS 回读）消费。任何依赖 `lost_count` 做"丢线持续时长"分析的脚本，现在只能看到 **0 或 31** 两个值，**全部连续帧信息丢失**。

**⚠️ 边界说明（避免误判影响面）**：主循环的这两个分支**只做 UI 显示**，不控制电机——真正的"丢线找回"动作在 `track_core.c:697-718`（`vt_step` 内部：保持舵量 + 双轮降到 `VT_LOST_CRAWL`，满 `VT_LOST_FRAMES=25` 拍约 500ms 才置 `VT_LOST`）。因此**后果不是"车少了 500ms 找回动作"**（那段仍在），而是"主循环侧的中间态消失 + 诊断量塌缩 + 死分支"。严重度定 **中**（必现、影响诊断与状态机表达），而非高。

**处置建议（仅方案，不改）**
- 方案一（推荐，最小改动面）：在 `vt_step`/`apply` 侧把它做回真计数器——`VT_LOST` 时 `++`（带上限 31），恢复时清零；两个阈值即恢复原意。
- 方案二（不改行为，只消除死分支）：把 `cpu0_main.c:3377` 的 `else if (> LOST_STOP_LIMIT)` 改为基于 `controller.fault==VT_LOST` 的直接判断，并在 `PID.h` 注明该变量已是布尔量。
- 方案三：删掉 `LOST_STOP_LIMIT` 分支与相关 UI 文案（承认该功能已退化）。
- **必须单独立项**，因为它会改变丢线时的实车行为（方案一会让车重新有"挣扎"动作），需配套实车验证。

### ⚠️ B-2（低）`blind_sr` 精确相等 + 饱和

**位置**：`user/cpu0_main.c:3095-3097`
```
if (line_out_center < 0) { if (blind_sr < 60000u) blind_sr++; } else blind_sr = 0u;
if (blind_sr == CAM_BLIND_AUTO_TICKS && !cam_saved_valid && !cam_saved_request) { ... }
```
**场景**：`CAM_BLIND_AUTO_TICKS = 3u`（`cpu0_main.c:423`），靠"采样拍恰好等于 3"触发一次盲区存帧。

### ⚠️ B-3（低）`ticks_per_ms` 除零保护不完整

**位置**：`code/track_adapter.c:88-90`
```
if(!ticks_per_ms){ticks_per_ms=IfxStm_getFrequency(&MODULE_STM0)/1000u;last_tick=now_tick;}
tick_remainder+=(unsigned)(now_tick-last_tick);last_tick=now_tick;

```
**后果**：`if(!ticks_per_ms)` 只在**赋值前**判断，赋值后未复查。若 STM 频率 < 1000Hz（本板 100MHz，物理不可能），`tick_remainder/0` → TriCore 除零 trap → 死机。
**建议**：赋值后再补一次 `if(!ticks_per_ms) ticks_per_ms=1u;`（纯防御）。

## 2. 有符号 / 无符号混用

### ⚠️ B-4（低-中）`inner` 算出负值后被转成 `uint32_t`

**位置**：`code/track_core.c:809-810`
```
inner = target*(100 - abs(c->steering)*55/100)/100;
c->target[0]=(uint32_t)(c->steering>0 ? inner : target);
c->target[1]=(uint32_t)(c->steering<0 ? inner : target);
```
**场景**：内轮差速。`abs(c->steering)` 若 **> 181**，则 `100 - abs*55/100 < 0` → `inner < 0` → `(uint32_t)(-x)` = 约 **4.29e9**。
**后果**：`c->target[i]` 变巨值 → 下游 `output = target*3.0f + ...` 被 `if(output>5500)output=5500` 夹住（**不会真的爆 PWM**），但会把 `c->pwm[i]` 顶到 5500、并把 `stall_ms` 判定点亮 → **误报堵转 → `vt_control_stop(VT_STALL)` 停车**。
**当前是否可达**：**不可达**。已核验 `c->steering` 有完整不变量：`:709` 显式 `clamp(-100,100)`、`:773` 由 `desired`(已 clamp) + `slew` 逼近、`:774`/`:775` 的 `reliable_steering` 也只是回抄同量 → 恒在 ±100 内 → `abs*55/100 ≤ 55`。
**建议**（防御性）：在 `:809` 前加 `int st = clamp(c->steering,-100,100);` 并用 `st`；或把 `inner` 下限钳到 0。**风险>收益，非必要不动。**

### ✅ 2.1 正面：`line_enc5/6` 的模运算写法是对的（勿改）

`(int)(int16)(uint16)(l-encoder_old[0])` 是全工程唯一处理"16 位定时器回绕"的地方，**写法正确**。若有人"简化"成 `(int)(l - encoder_old[0])` 就会在回绕时得到巨大正数 → `vt_step:679` 的 `speed>2500u` 误判 → 立即 `VT_ENCODER` 停车。**建议在代码里加一行注释锁住这个写法**（当前无注释）。

### ⚠️ B-5（低）负值字段转 unsigned 的"补码契约"未在头文件声明

**位置**：`user/cpu0_main.c:1925-1931,1979,1985,1994-2000,2006,2018`
```
line_senior_report.enc5 = (unsigned)(int)line_enc5;        /* 可能为负 */
line_senior_report.gyro_bias = (unsigned)(int)line_gyro_bias;
line_senior_report.acc_z = (unsigned)(int)line_acc_z;
```
**场景**：这些物理量可为负，代码用"位模式"上报，依赖读端按补码解释。
**后果**：`ring_diag.h:20` 明确写了 *"Signed values use two's complement"*，但 **`LineSeniorReport` 的头文件没有这句**。读端（DAS/脚本）若按无符号解释 → 负值显示成 ~4.29e9。
**建议**：在 `LineSeniorReport` 定义处补一行同样的说明（纯注释）。

### ℹ️ 2.2（信息）float → int 的 UB 边界

`cpu0_main.c:1898,1901,3284,3287`：`(unsigned)(int)(line_out_deviation * 1000.0f)`。

### ❗ B-8（**中**）`controller` 缺 volatile —— ISR 写、主循环读

**位置**：`code/track_adapter.c:8` `static VTControl controller;`（**无 volatile**）

**证据链**
- **ISR 上下文写**：`isr.c:47-55` `IFX_INTERRUPT(cc60_pit_ch0_isr,...) → TrackControlTick()`；`TrackControlTick`（`track_adapter.c:85-143`）全程改写 `controller`（`vt_step`、`vt_control_stop`、`vt_control_start`）。
- **主循环上下文读**：
  - `track_vision.c:26` `tracker.edge_mode = TrackEdgeMode();` → `track_adapter.c:37` `vt_edge_mode(&controller)`（读 `controller.phase`）
  - `track_vision.c:28` `br2_process(..., TrackRunning(), ...)` → `track_adapter.c:38` `return controller.active;`
  - 而 `cam_line_all()` 由主循环 `cpu0_main.c:2778` 调用。
- 对照：**同一个文件里的 `frame` 特意标了 volatile**（`:9`），`controller` 没有——不一致，说明是遗漏而非有意。

**后果**：编译器在**主循环侧**看 `controller` 是普通对象，可把它**缓存进寄存器/在函数间重排**（尤其一旦开 LTO 或函数被内联）。TriCore 上单字读不会撕裂，所以现在**没爆**——但这属于"靠编译选项侥幸"。典型爆点：`TrackEdgeMode()` 被内联进 `cam_line_all` 后跨 ISR 读到**过期 phase** → 环岛段的 `edge_mode` 判断滞后一拍（环岛逻辑对相位极敏感）。
**建议**：`static volatile VTControl controller;`（`vt_step` 形参需相应改为 `volatile VTControl*` 或内部逐字段读）。**注意**：这一改动会触碰 vt_step 签名，必须与环岛改动**分开立项**。

### ⚠️ B-9（低-中）显式剥离 volatile：`(const VTFrame *)&frame`

**位置**：`code/track_adapter.c:112`
```
vt_step(&controller,(const VTFrame *)&frame,milliseconds,dt,...);
```
**场景**：`frame` 是 `volatile VTFrame`（ISR 要读、主循环要写），这里用强制转换把 volatile **丢掉**，`vt_step` 内部（`element()` 反复读 `v->open_left/fork/valid/...`）看到的是非 volatile 视图。
**后果**：C 标准允许"显式 cast 掉 volatile 后按普通对象访问"，但编译器**不再保证每次都回内存取**。当前之所以安全，是因为发布端 `TrackVisionPublish`（`track_adapter.c:32-35`）把整帧拷贝放在 `interrupt_global_disable()` 临界区里，且 `cam_line_all` 是主循环上下文（会被 ISR 抢占，不会与 ISR 并发跑）。→ **结论：正确但依赖时序论证，不是靠类型保证。**
**建议**：把 `vt_step` 形参改 `const volatile VTFrame*`（或发布端改为"先拷到一张非 volatile 影子结构再传"），让类型系统替我们兜住。属清理项。

### ⚠️ B-10（低 · 文档/前提失效）"中断不嵌套"的论证已不成立

**位置（注释）**：`code/cam_image.h:38-48`（v079 帧快照说明）写着：
> 「复制期间不会被打断（DMA 中断优先级 60 > VSYNC 43，**TC264 默认中断不嵌套**）」

**位置（代码）**：`user/isr.c:49,60,70,80,91,110,143,165,...` —— **每一个** `IFX_INTERRUPT` 函数体第一行都是 `interrupt_global_enable(0);`（按 `isr.c:43-44` 的自述，此调用即"开启中断嵌套"）。

**后果**：v079"三层保险"的第①层论证前提（不嵌套 ⇒ `cam_frame_snap` 的 22.5KB 复制不可被打断）**不成立**。实际安全性来自另一条事实：`cam_isr_buf` 的唯一写者就是 `cam_frame_snap` 自己，没有第二个写者——**结论侥幸成立，但理由写错了**。风险在于：将来若有人在 VSYNC ISR 里也动 `cam_isr_buf`（很自然的优化想法），依据这段注释会**以为安全**。
**建议**：把该注释改为"`cam_isr_buf` 只有单一写者（DMA 完成 ISR），复制期间即便被更高优先级中断打断也不会有人改它"，并注明 ISR 已开嵌套。

## 4. 数组越界（CAM_H / CAM_W 索引）

### ❗ B-11（**中**）`CAM_W/CAM_H` 与 `VT_W/VT_H` 是两处独立定义的同一事实

**位置**

- `libraries/zf_common/zf_common_headfile.h:122-123` `#define CAM_W MT9V03X_W` / `#define CAM_H MT9V03X_H`
- `libraries/zf_device/zf_device_mt9v03x.h:81-82` `MT9V03X_W (188)` / `MT9V03X_H (120)`

**关键耦合点**：`code/track_vision.c:27`
```
vt_analyze(&tracker, &cam_bin[0][0], ...);
```
`vt_analyze`（`track_core.c`）把这块内存当 **扁平 `[VT_H][VT_W]`** 用（如 `bin[y*VT_W+x]`，`y∈[0,110]`），而 `cam_bin` 的声明是 `uint8 cam_bin[CAM_H][CAM_W]`。
**后果**：当前两边都是 **188×120 → 完全吻合**（已实测核验：`vt_analyze` 最大索引 `110*188+187 = 20867 < 22560`）。但这是**隐式契约**：任何人把 `MT9V03X_W/H`、或 `VT_W/VT_H`、或裁剪窗口改一下，就变成**静默错位/越界**（不报错、可编译、行为诡异）。
**建议**：在 `track_core.h` 里加编译期断言把两者钉死，例如
`#if (VT_W != CAM_W) || (VT_H != CAM_H) #error "VT_* must equal CAM_*" #endif`（`track_core.h` 已 include `<stdint.h>`，只需再确保 CAM_* 可见）。**这是零行为改动的高价值护栏。**

### ⚠️ B-12（低）`SNAP_WORDS` 假设尺寸能被 4 整除

**位置**：`code/cam_image.c:254`
`#define SNAP_WORDS ((uint32)CAM_H * (uint32)CAM_W / 4u)`，配合 `:273` `d[i]=s[i]` 按 uint32 复制。
**后果**：当前 `120*188=22560`，`22560/4=5640` **整除**，快照完整。若尺寸变成非 4 倍数，尾部的 1~3 字节**不会被复制**（静默丢像素）；且 `snap_copy32` 按 uint32 递增，理论上还会**多读**到数组尾后（对齐上目前恰好安全）。无断言。
**建议**：加 `_Static_assert((CAM_H*CAM_W) % 4u == 0u, ...)`，或改为按字节循环。

### ⚠️ B-13（低）`panel_rows` 写入上界与容量**恰好相等**（零余量）

**位置**：`user/cpu0_main.c:648` `static uint16 panel_rows[320 * 4];`
**写入点**：`:767` `panel_rows[index]`，`index < w*rows ≤ 320*4 = 1280`（`fill_rect:752` 已把 `w` 裁到 `320-x`）；
`:809` `panel_rows[dy*b->width + column]`，`dy<rows≤4`、`column<b->width`，且 `:791` 已保证 `x + b->width ≤ 320`。

### ⚠️ B-15（低）`trace_gyro` 无钳位直接窄化

**位置**：`user/cpu0_main.c:3053` `trace_gyro[rec_frames] = (short)line_gyro_f;`
**场景**：`line_gyro_f` 是 `volatile int`（滤波后角速度原始值）。
**后果**：若 >32767 或 <-32768 会**静默回绕**（记录通道出现"镜像跳变"，误导事后诊断）。同区块的 `trace_steer`/`trace_speed` 都有显式钳位，**只有它没有**——不一致。
**建议**：加 `clamp(-32768,32767)`，与邻居保持一致。

### ⚠️ B-16（低-中 · 当前不可达）`draw_digits` 的 `char text[8]` 无长度保护

**位置**：`user/cpu0_main.c:836` `char text[8];` + `:845` `sprintf(text, "%u", value);`
**场景**：`draw_digits` 是全屏数字绘制的通用出口。
**后果**：`%u` 最大 10 位数字 + `'\0'` = **11 字节** → 溢出 `text[8]` **最多 3 字节**，落在栈上，可能踩坏相邻局部变量/保存寄存器。**已逐个核查全部 11 个调用点的实参值域**：

| 调用点 | 实参 | 最大位数 | 结论 |
|---|---|---|---|
| `:1073/1313/1433` | `(unsigned)line_out_center`（**有 `if(<0)` 兜底**） | 3 位（0..127） | ✅ |
| `:1196/1334` | `spd`（编码器和的一半，**已显式 `if(spd>9999u)spd=9999u` 钳位**，注释自述"防越界"） | 4 位 | ✅ |
| `:1214/1439` | `img_threshold` | 3 位 | ✅ |
| `:1220` | `line_out_black_pixels`（≤128） | 3 位 | ✅ |
| `:1226` | `line_out_lost_count`（0/31） | 2 位 | ✅ |
| `:1289` | `rec_frames`（≤2000） | 4 位 | ✅ |
| `:1295` | `TRACE_MAX`（2000） | 4 位 | ✅ |
| `:1445` | `line_out_white`（≤128） | 3 位 | ✅ |
| `:887/920/929`（经 `draw_signed_int/float`） | 有界 | ≤4 位 | ✅ |

**结论**：当前**不可达**（≤4 位 vs 容量 7 位+NUL）。但这是**纯靠调用方自律**的接口——**危险写法已经就位**。佐证：`cpu0_main.c:1193/1331` 作者自己写了 `if (spd > 9999u) spd = 9999u;` 并注明"限幅，防越界"，说明**当时就知道 `text[8]` 有这条隐形上限**，只是把守卫写在了**调用点**而不是函数内。特别提醒：**任何 `(unsigned)(负值)` 传进来就是 10 位**——这正是为什么 `:1070/1310/1430` 那三处 `if(line_out_center<0) ... else` 的兜底**必须保留**（去掉就是必现栈溢出）。
**建议**：三选一——(a) `char text[12];`；(b) `snprintf(text, sizeof text, "%u", value);`；(c) 函数头加 `if (value > 9999999u) value = 9999999u;`。方案 (a) 最省事。

### ℹ️ 5.2（建议）`trace_center` 的钳位不对称

`(signed char)(line_out_center <= 127 ? line_out_center : 127)` 只钳上界。当前正确（`line_out_center` 唯一负值是 -1，`signed char` 装得下）。但若未来 `CalculateCenterLine` 改成返回 -1/-2 之类的错误码，就会静默回绕。**建议补下界钳位**（`< -128 ? -128 :`），零成本。
