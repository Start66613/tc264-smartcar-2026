## 1. 方法：三条独立证据链交叉验证

本轮的判定不靠"肉眼看没人调用"，而是让**链接器自己作证**，再用两条独立方法复核。

### 证据链 1｜链接器 map 的 `Removed Sections` 表（最硬）

TASKING 链接器会为**每一个被丢弃的节**记录原因。map 第 11833 行起有这张表，字段为
`Section | File | Library | Symbol | Reason`，本工程相关条目的 Reason 全部是 **`unreferenced`**。

> 这是"能被证明的死"，不是推测：链接器做了完整的可达性分析（含迭代收敛——A 调 B、A 死了 B 也死）。

### 证据链 2｜链接器 map 的 `Cross References` 表（反向验证）

map 第 3859 行起：`Definition file | Definition section | Symbol | Referenced in`。
用它反查**保留下来的**符号各自的引用者。结果是：**所有存活符号都至少有一个引用者，没有任何"引用列为空"的条目**——说明证据链 1 的清单是完备的，没有漏网。

### 证据链 3｜`objdump -t` 符号表按 `.src` 归组（独立于 map）

```
E:/tool/Dev-Cpp/MinGW64/bin/objdump.exe -t Debug/TC264_VisionTrack.elf
```
`-t` 可用（能列出 423 个 `F` 型符号，且以 `<name>.src` 标记归属源文件），
但 **`-d` 反汇编不可用**：`objdump: can't disassemble for architecture UNKNOWN!`
（MinGW 的 binutils 2.37 不含 TriCore 后端）。因此本轮**没有、也无法**用 objdump 做指令级交叉引用，改用 `-t` 做符号级复核。

复核结果：上述 14 个死函数**全部不在符号表中**；而静态函数（如 `cam_ostu`、`clamp`、`snap_copy32`）**都在**符号表里 → 说明它们活着，没有误杀。

### 证据链 4｜源码回查（剔除注释与字符串后做词边界匹配）

对每个被判死的符号，回到活跃源码（37 个 .c/.h，**已排除** `.bak_*` / `.rejected` / `.marked`）中，**先剥离块注释、行注释、字符串与字符字面量**，再做 `\bword\b` 匹配，得到"源码里还有没有真引用"。

## 7. 两处"重复实现"隐患（与死代码强相关）

### 7.1 🔴 `LineStartupLimit` 的公式被内联复制到 `track_core.c`

```c
/* code/control_time.c:2  ——  死，已内联 */
int LineStartupLimit(unsigned elapsed_ms, int full_target)
{
    if (full_target <= 150 || elapsed_ms >= 2000u) return full_target;
    return 150 + (int)((unsigned)(full_target - 150) * elapsed_ms / 2000u);
}
```
```c
/* code/track_core.c:779  ——  活，实车生效 */
if(now-c->start_ms<2000u){int ramp=150+(int)((now-c->start_ms)*310u/2000u);if(target>ramp)target=ramp;}
```

## 9. 附：本轮顺带发现（属方向 C，**修正先前审计的前提**）

因为要"剥离注释再查引用"，我在读取时撞上了一个**重要事实**——顺手核清了。

### 9.1 先前记录的"cpu0_main.c 有 7000+ 个 U+FFFD 乱码"**是假象**

| 读法 | 替换字符数 |
|---|---|
| 按 UTF-8 解码 `cpu0_main.c` | **7182** ← 先前记录的数字来源 |
| 按 **GBK** 解码 `cpu0_main.c` | **29** |

`cpu0_main.c` **是 GBK 编码文件**，中文注释**完全正常可读**：

```
行   4 | * TC264 Opensourec Library 即（TC264 开源库）是一个基于官方 SDK 接口的第三方开源库
行   7 | * Copyright (c) 2022 SEEKFREE 逐飞科技
行 2825 |         /* ★★★ v066：2D 几何判据（替代 1D 时代的脆弱判据）★★★
行 2890 |         /* ---- 旧的 1D 判据（已停用，保留代码以便对照/回退）---- */
```

"7182 个乱码"＝**把 GBK 当 UTF-8 解码**的必然产物，不是文件坏了。

### 9.2 真正的乱码只有 6 行 / 29 个字符

`cpu0_main.c` 是**混合编码**：绝大部份 GBK，但下面 6 行是 **UTF-8 中文混进了 GBK 文件**（连 GBK 都解不出来），这才是需要修的：

| 行 | 内容开头 |
|---|---|
| 420 | `/* v142 盲区自动存档（诊断）：车运行中连续 3 个采样拍（≈195ms）...` |
| 421 | `   存入 line_trace/cam_saved_mid（复用 P20.7 存档通道）。缓冲未读出时不覆...` |
| 422 | `   线恢复后再盲区可再抓。元数据：auto 0=手动 1=盲区自动。 */` |
| 3086 | `/* v142 盲区自动存档（诊断，只读行车状态、不参与控制）：` |
| 3087 | `   车运行中连续 CAM_BLIND_AUTO_TICKS 个采样拍无有效线（≈195ms）...` |
| 3088 | `   缓冲未读出（valid/request 已置）时不覆盖；线恢复后再盲区可再...` |

**特征**：全是 v142 新增的注释——说明**新写的注释用了 UTF-8，而文件本体是 GBK**。这是编辑器编码设置漂移导致的，会持续产生新的坏行。

### 9.3 全工程编码分布（供方向 C 排期）

| 类别 | 文件数 | 文件 |
|---|---|---|
| 🟢 **纯 UTF-8（正常）** | 7 | `track_core.c/h`、`big_ring.c/h`、`track_adapter.c`、`ring_diag.h` |
| 🟡 **纯 GBK（中文正常，只是编码不同）** | 14 | `CCD.c/h`、`PID.h`、`PM.c/h`、`TX.c/h`、`cam_image.c/h`、`cam_line.h`、`dianji.c/h`、`duoji.c/h`、`finish_line.c/h`、`cpu1_main.c`、`isr.c/h`、`isr_config.h` |
| ⚪ 纯 ASCII / 两可 | 9 | `PID.c`、`cam_line.c`、`control_time.c/h`、`ring_diag.c`、`track_adapter.h`、`track_vision.c`、`cpu0_main.h`、`line_ui_assets.*` |
| 🔴 **混合 + 真乱码** | **1** | `user/cpu0_main.c`（GBK 为主 + 6 行 UTF-8 混入） |

**关键风险**：`track_core.c/h`（UTF-8）**被** `cpu0_main.c`（GBK）**include**。当前中文只出现在注释里，编译无影响；但这意味着**同一份编译单元链上存在两种源码编码**，任何一次"另存为"都可能把一侧搞坏。
→ 方向 C 的"一次性修复方案"必须**同时**处理"统一编码"与"这 6 行"两件事，不能只修 6 行。
